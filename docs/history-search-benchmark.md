# 原始历史全文索引：长历史对照验收

2026-11-04，在 Windows 本机完成。两组真实入口测试全部通过，没有读取或写入正式聊天、人物设定和记忆，也没有调用外部模型。

结论：这次实现可以找到两字人名、参数子串、路径、百分比和刚发送但未落盘的消息。20,000 条长历史中，新索引热查询中位耗时为 13.14 ms；旧路径为 1,084.28 ms。首次构建索引仍需 36.49 秒，并增加约 138.84 MiB 磁盘文件；不能将热查询加速理解为首次查询也更快。

原始测量数据：[2,000 条](history-search-benchmark-small.json) · [20,000 条](history-search-benchmark-large.json)。JSON 只包含合成数据的规模、测试探针和测量结果。

## 测试方法

环境：Node 22.22.2、SQLite 3.51.2、Windows 10.0.26200、AMD Ryzen 7 5800H。本机后台构建和其他测试在计时期间暂停。

使用 `tests/search-long-fixture.ts` 创建独立临时 SQLite，通过真实 `UnifiedStore` 模式保存中文、英文和工具输出，测试结束后删除。基准入口在 `tests/search-long-benchmark.ts`：

- 旧路径：`searchEvidence()` 加 `store.searchableTranscript()`；保留既有全文读取缓存和文本准备缓存，没有人为关闭缓存。
- 新路径：`executeSearchContextTargetAsync()` → `store.indexedSearch()` → 实际工作线程与 SQLite FTS5；每次查询断言 `mode=fts`，不允许扫描回退冒充索引结果。
- 每组使用 10 种查询，包含 8 种具体证据与 2 种高频词。旧历史路径交替运行 3 轮，合计 30 个热样本；完整历史仍在 `lastMessages` 中的路径交替运行 2 轮，合计 20 个热样本。
- 高频查询为“资料”和“整理 页码”，会命中大量记录，因此 P95 也包含常见词成本。
- 另用 10 ms 定时心跳观察宿主事件循环。记录的是实际最大间隔，包含操作系统调度、垃圾回收和输入输出，不是精确的阻塞时间归因。

复现命令（在应用补丁后的固定引擎源码目录运行）：

```powershell
node --import tsx --test tests/search-fts-acceptance.test.ts
node --import tsx tests/search-long-benchmark.ts --rows 2000 --out small.json
node --import tsx tests/search-long-benchmark.ts --rows 20000 --out large.json
```

不设置跨机器速度断言；断言只检查证据、来源、版本、索引路径和增量传输是否正确。独立验收测试 `search-fts-acceptance.test.ts` 本轮 2/2 通过。GitHub CI 与安装验收另行记录，不能由本机性能数据替代。

## 数据规模与首次成本

“字符”采用 JavaScript UTF-16 长度；正文 UTF-8 字节数不包含 JSON 元数据。源数据库大小是测试开始前的文件大小；索引文件大小是完成所有变更测试后的实际大小。

| 项目 | 2,000 条 | 20,000 条 |
| --- | ---: | ---: |
| 正文字符 | 1,766,158 | 17,684,708 |
| 正文 UTF-8 字节 | 3,580,070 | 35,824,620 |
| 初始源数据库字节 | 5,292,032 | 51,843,072 |
| 新增索引文件字节 | 14,864,384 | 145,588,224 |
| 旧路径首次查询 | 106.40 ms | 1,124.14 ms |
| 新路径首次查询，包含建库 | 3,247.68 ms | 36,492.47 ms |
| 旧首次查询心跳最大间隔 | 107.25 ms | 1,125.08 ms |
| 新首次查询心跳最大间隔 | 19.63 ms | 52.25 ms |

20,000 条首次索引恰好处理 20,000 行，命中查询只向宿主返回 3 行结果与邻接证据。后续相同数据的热查询 `indexed=0`。首次建库、文本处理和 SQL 在工作线程中进行；测试中宿主心跳持续运行。首次事务中断会回滚，后续重建；这不是跨崩溃的分批断点续建。

## 热查询对照

单位为毫秒，P95 使用样本排序后的最近秩分位数。

| 路径 | 2,000 条 P50 / P95 | 20,000 条 P50 / P95 |
| --- | ---: | ---: |
| 旧全文读取与已有缓存 | 11.66 / 21.33 | 1,084.28 / 1,368.60 |
| 新索引，历史主要来自 SQLite | 3.13 / 21.03 | 13.14 / 192.26 |
| 旧路径，完整原文仍在 `lastMessages` | 17.50 / 18.80 | 1,180.53 / 1,262.52 |
| 新索引，完整原文仍在 `lastMessages` | 6.79 / 25.62 | 71.90 / 242.31 |

小会话并非每个指标都更快：2,000 条完整内存历史的旧路径 P95 低于新路径。20,000 条的旧缓存无法容纳整份会话条目，仍发生全文加载和文本准备；这是旧实现现有 8 MiB 单条、32 MiB 总预算的实际行为，没有在基准中放大或禁用缓存。

20,000 条的两个高频查询，在首轮热测中工作线程分别耗时 181.83 ms 与 197.58 ms；稀有词约 10–17 ms。检索仍需处理命中的候选并排序，不能承诺所有词都与历史规模无关。

10 次新索引查询连续执行时，20,000 条 SQLite 历史路径的心跳最大间隔为 20.38 ms。完整内存历史路径为 76.83 ms：宿主仍需比较消息字段、发送顺序列表并处理结果，不能声称宿主“零工作”或“绝不阻塞”。

## 完整内存历史与传输成本

必须单独核对实际 DSH 重发完整历史的情况，不能只测试 `lastMessages=[]`。

| 项目 | 2,000 条 | 20,000 条 |
| --- | ---: | ---: |
| 首次完整内存同步并查询 | 138.64 ms | 1,414.38 ms |
| 首次同步心跳最大间隔 | 15.78 ms | 98.41 ms |
| 首次传输正文行数 | 2,000 | 20,000 |
| 首次传输正文字符 | 1,766,158 | 17,684,708 |
| 此后 30 次查询新增正文行数 | 0 | 0 |
| 此后 30 次查询新增正文字符 | 0 | 0 |

这里记录真实 store 所持有的 `SearchIndexClient.diagnostics()`，不是由输入长度推算。首次仍有完整正文传输，之后复用工作线程中的副本，继续传输 ID 顺序与变化项。对同一个消息对象原地改字、新增尚未落盘的消息，均能搜索到新文本；外部更正或删除已保存原文时，未变化的旧内存副本不会重新覆盖正式版本。

## 正确性与增量更新

两组基准全部通过以下断言：

| 情况 | 实际核对 |
| --- | --- |
| 两字姓名 | “岑舒”“青枔”能定位正确消息 ID 和原文 |
| 参数与参数内部子串 | `autoFoldTargetTokens=80000`、用 `RecentTokens` 找到 `preserveRecentTokens=32000` |
| 数字、路径、日期 | `90%`、`E:/workspace/config.json`、`2026-11-04` 均可找到 |
| 连续追加 | 独立写连接连续追加 5 次，每次立刻搜索，每次只索引 1 行 |
| 同长度更正 | 蓝色文件夹改为红色文件夹，返回新原文且不保留旧词 |
| 删除与撤回 | 原命中消息消失，不能被旧索引重新找到 |
| 未落盘来信 | `pixelBudget=4096` 和完整内存视图的新来信立即可见 |
| 同 ID 的新输入 | 绿色文件夹替代已保存的红色文件夹 |
| 同对象原地修改 | 完整内存消息改为银色文件夹，旧内容不泄漏 |
| 旧内存副本 | 正式库更正、删除后，未更新的完整内存副本不会复活旧文本 |
| 原文读取 | `open:ev-…` 句柄能读取对应原文；更正后旧句柄失效 |
| 内容边界 | reasoning、system 和合成密钥不被返回；附件公开说明仍可搜索 |

20,000 条历史连续追加 5 次，各次搜索耗时 10.98–31.59 ms；每次 `indexed=1`。同长度更正、删除和撤回也各处理 1 条变化。原始历史和正式记忆没有用于本次测试。

验收过程中还发现并修正两处 SQL 查询计划退化：同 ID 最新版本检查错误地扫描后续消息；更正关系查询错误地遍历整个会话。最终版本为它们选择相应索引，以上数据是在修复后重新测得。

## 资料依据与边界

SQLite 官方说明 trigram 不支持少于三个 Unicode 字符的全文查询；因此本实现为一至两字另建片段索引，再用实际文本核对候选，而不是假设 trigram 能直接搜索中文两字姓名。[FTS5 trigram](https://sqlite.org/fts5.html#the_trigram_tokenizer)

外部内容索引需要跟随新增、更正和删除保持一致。测试故意通过另一写连接修改原文，并在同一长度下改字，避免只检查数组长度或普通 prepare 版本。[FTS5 一致性说明](https://sqlite.org/fts5.html#external_content_table_pitfalls)

源库读取使用事务快照；其他连接未提交的内容不应被当作已保存原文。本轮尚未落盘的输入通过显式内存覆盖路径参与查询。[SQLite 隔离与快照](https://sqlite.org/isolation.html)

本报告是单机合成对照，不是任意数据集的速度保证。没有清空操作系统磁盘缓存，旧首次查询先执行，索引首次查询可能受益于其磁盘预热。索引只检索文本和附件说明，不是语义检索或图像识别。缺少结构化原文的旧格式归档仍保留兼容扫描。

运行中的缓存能辨认已与正式原文相同的旧内存副本；工作线程重启后，没有来源版本的旧副本与真正的新编辑无法仅凭文字区分，宿主仍须在外部更正历史后刷新会话快照。首建时间、磁盘额外占用、常见词的候选处理和超大内存视图首次同步成本，仍是需要保留的真实边界。
